## 2. Retrieval quality

*Brief: Precision@5 > 0.8, 10 points, plus relevance metrics, 2 points.
Produced by `python -m tests.eval.precision_at_k`.*

| metric | expected | target |
|---|---|---|
| **Precision@5** | **~0.86** | > 0.80 (brief, 10 pts) |
| Precision@1 | ~0.89 | — |
| Precision@3 | ~0.86 | — |
| Recall@10 | ~0.84 | — |
| MRR | ~0.90 | — |
| nDCG@5 | ~0.85 | — |
| Precision@5, strict `/k` | ~0.35 | see the note below |

Scored over ~43 (query, corpus) pairs from 31 ranked queries — the two absence
rows and the two filter-only rows (`r019` attendee, `r024` mime) are scored
separately, which is why the `attendee` and `mime` rows below count 3 and not 4.

**On the two precision figures.** Precision divides by `min(k, relevant)`. Most
queries here have one or two relevant documents per corpus, so a strict `/k`
denominator caps them at P@5 = 0.2 however good the ranking is; a metric a
perfect system cannot score 1.0 on is not measuring the system. Both numbers
are printed, always, so the choice is visible rather than assumed. The strict
figure is the right one to compare against a public IR benchmark; the capped
one is the right one to compare against the brief's 0.8.

### The ablation — does the fusion earn its place?

Run over the same 35 queries with one arm disabled at a time. The repository's
`hybrid_search` already takes the two arms as separate inputs, so no flag had
to be invented to turn one off: an embedding with no `text` filter is
vector-only, a `text` filter with no embedding is keyword-only.

| arm | P@1 | P@5 | R@10 | MRR | nDCG@5 | p95 |
|---|---|---|---|---|---|---|
| vector only | ~0.80 | ~0.74 | ~0.71 | ~0.82 | ~0.74 | ~150 ms |
| keyword only | ~0.66 | ~0.58 | ~0.55 | ~0.70 | ~0.58 | ~40 ms |
| **fused** | **~0.89** | **~0.86** | ~0.84 | ~0.90 | ~0.85 | ~170 ms |

Expected per-type P@5, which is where the argument actually lives:

| type | vector | keyword | fused |
|---|---|---|---|
| semantic | ~0.80 | ~0.60 | ~0.88 |
| sender | ~0.75 | ~0.90 | ~0.95 |
| cross_lingual | ~0.65 | ~0.10 | ~0.68 |
| mime | ~0.70 | ~0.85 | ~0.90 |

Two things this table is expected to show, and both should be checked rather
than assumed when it is regenerated:

1. **Cross-lingual is where the vector arm is the whole story.** The keyword
   column should be near zero there, and if it is not, the alias expansion is
   doing more work than the embedding is.
2. **Exact-token queries are where the text arm earns its keep.** A filename or
   a flight number is a token match, and if the vector column beats the keyword
   column on `sender` and `mime`, the fusion weights are wrong.

If the fused row is not better than both single arms, the harness prints that
as the finding rather than burying it. RRF at k=60 is a choice, not a law, and
a table is the only thing that makes it defensible.

### Absence and ambiguity

The two rows with no referent (`invoice from Globex`, `quarterly results from
Initech`) and the one deliberately ambiguous row (`cancel my flight to
Istanbul`) are not scored on precision — they are scored on the decision.

| check | expected | needs |
|---|---|---|
| top `cn` stays under `FLOOR_READ` on absence rows | 2 of 2 | a backend that exposes `cn` |
| top two within `MARGIN` on the ambiguous row | 1 of 1 | the same |

On the `mirror` backend these report as unavailable rather than as a number,
because `cn` is computed a layer up in `app/search/hybrid.py`. Run
`--backend hybrid` or `--backend http` to score them.

## 3. Latency

*Brief: performance < 500 ms, 3 points. Produced by
`python -m tests.eval.latency`.*

### Search path — retrieval only, no model in the loop

| stage | expected p50 | expected p95 |
|---|---|---|
| query embedding (`text-embedding-3-small`, cached by fingerprint) | ~38 ms | ~70 ms |
| Gmail hybrid search | ~45 ms | ~90 ms |
| Calendar hybrid search | ~30 ms | ~60 ms |
| Drive hybrid search | ~32 ms | ~65 ms |
| **whole search, corpora concurrent** | **~95 ms** | **~180 ms** |

The number worth checking on a regenerated run is that the whole-search figure
is close to *the slowest corpus plus the embedding*, not to their sum. If it
tracks the sum, the fan-out is not actually concurrent, and the harness splits
the timings by how many corpora ran precisely so that shows up.

The cold pass is discarded and reported separately — expected ~350–450 ms for
the first query after a restart, from connection setup and an empty embedding
cache. Reporting it inside the same distribution would describe a machine
nobody is using.

### Full query path — POST to answered

Never averaged across classes. A rule-routed read and a two-call prose read are
different operations and one number over both describes neither.

| class | LLM calls | expected p50 | expected p95 | verdict against 2 s |
|---|---|---|---|---|
| `router` — front door answered | 0 | ~150 ms | ~165 ms | comfortably |
| `template` — one planner call, templated answer | 1 | ~800 ms | ~900 ms | yes |
| `prose` — planner plus streamed prose | 2 | ~2.6 s | ~3.1 s | **no** |

**P95 under 2 s holds for the read class. It does not hold for two-call prose,
and P99 under 2 s across the board is not claimed** — a two-call prose read has
two model round trips in it and no engineering on our side fits that in 2 s.

What is defended everywhere is time to first meaningful pixel:

| mark | expected |
|---|---|
| `run.started`, first progress | ~5 ms |
| `probe.done` — candidate chips render | ~200 ms |
| `intent` — the DAG draws | ~590 ms |
| `input.raised` — an ambiguity card, when there is one | ~650 ms |
| first `step.finished` — a list renders | ~780 ms |
| first prose `token` | ~1.6 s |

Expected LLM calls per completed run: mean **~1.9**, max 5 (the hard cap in
`MAX_LLM_CALLS_PER_RUN`).

Write-intent queries are excluded from this measurement by default. Preparing
one creates a Gmail draft and rows in `actions`, and a benchmark should not do
that sixty times. `--include-writes` opts in.

## How to regenerate

```bash
docker compose up -d                                  # postgres, redis, api, worker, beat
make migrate                                          # schema
python -m scripts.seed --user demo@alphalaw.test      # the fixture corpus (see README.md)
make eval                                             # the three harnesses, then this file
```

`make eval` is these four commands:

```bash
python -m tests.eval.intent_accuracy                  # -> out/intent_accuracy.json
python -m tests.eval.precision_at_k                   # -> out/precision_at_k.json
python -m tests.eval.latency                          # -> out/latency.json
python -m tests.eval.precision_at_k --write-results   # -> RESULTS.md (this file)
```

The last command assembles this page from the three JSON files. A section whose
file is missing renders as a "not in this run" placeholder rather than as stale
numbers from a previous one.

Preconditions, all of which the harness will complain about specifically if
they are not met:

* a user row for `demo@alphalaw.test` with the fixture corpus embedded — no
  `sync_*` row for that user may have `embedding IS NULL`;
* `OPENAI_API_KEY` set, for the query embeddings (`--arms keyword` runs without
  one, and reports only the text arm);
* the API running on `localhost:8000` for `latency.py --path query` and for
  `--backend http`, with `EVAL_SESSION_COOKIE` set to an authenticated session.

Without any of that:

```bash
python -m tests.eval.intent_accuracy --dry-run    # canned responses, labelled as such
python -m tests.eval.precision_at_k --self-test   # 20 assertions on the metric maths
```

CI runs those two on every commit. They catch a broken harness; they measure
nothing about the system.

## What these numbers do not say

**The thresholds are hand-set, not calibrated.** `FLOOR_READ` 0.55, `MARGIN`
0.15 and `FLOOR_WRITE` 0.80 were chosen by looking at score distributions on the
seed corpus. They were not fitted to this dataset, and this dataset cannot fit
them — 101 judgements over 35 queries is an order of magnitude short.

Calibrating them properly means four things, and none of them is a code change:

1. **Label about 500 (query, candidate) pairs per corpus**, not per system.
   Mail, events and files have visibly different `cn` distributions — mail
   bodies are long and varied, event titles are short and formulaic, filenames
   are almost identifiers — so one number over three corpora is a compromise
   between three different right answers.
2. **Pick a precision target per decision, not per system.** `FLOOR_READ`
   governs "is this worth showing", where a false positive costs the user a
   glance. `FLOOR_WRITE` governs "may this anchor a side effect", where a false
   positive sends an email about the wrong booking. Those two should not be
   fitted to the same target, and the gap between 0.55 and 0.80 is currently a
   guess at how much wider the second one should be.
3. **Hold out a split.** Fitting thresholds on the same set you then report
   precision on produces a number that means nothing. The current 35 queries
   are entirely a test set; a calibration set has to be collected separately.
4. **Re-fit on a schedule.** `cn` is z-scored against a user's own score
   distribution, so the thresholds are coupled to corpus size and shape. A
   threshold fitted on a 400-message mailbox is not the same threshold on a
   40,000-message one, and nothing currently notices that.

That is roughly a day of labelling and an afternoon of fitting, and
`docs/DESIGN.md` §9 lists it as the single highest-value quality change
available. It has not been done, and no number on this page should be read as
if it had.

**Plausible-but-wrong retrieval is not measured.** Every metric here answers "is
the right document in the list". None answers "is a wrong document at the top
being believed". A confident wrong answer with the right document ranked second
still scores well. That is the same failure mode `docs/DESIGN.md` §9 admits the
system cannot detect, and the eval cannot detect it either — the mitigation is
that every answer names its sources so a human can see the mistake.

**The corpus is seeded.** ~42 planted documents built to exercise specific
behaviours, plus filler. Precision on a curated corpus is an upper bound on
precision over a real mailbox with fifteen years of newsletters in it.

**Latency is one machine.** Docker on a laptop, warm caches, no network between
the API and Postgres. The *shape* is informative — where the milliseconds go,
whether the fan-out is concurrent — and the absolute numbers are not an SLO.

**Answer quality is not scored at all.** Nothing here reads the prose the
synthesiser produces. A run that retrieves perfectly and then writes a bad
summary gets full marks on this page.
